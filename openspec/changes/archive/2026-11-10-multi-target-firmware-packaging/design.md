# Design

## Context

See `proposal.md` for motivation. nesigner targets 7 distinct ESP32 chips (`esp32s3`, `esp32s2`, `esp32c3`, `esp32c5`, `esp32c6`, `esp32p4`, and `esp32s31`), each requiring distinct `sdkconfig.defaults.<target>` files, clock configurations, and transport layers (TinyUSB CDC-ACM vs Native USB Serial/JTAG).

## Goals / Non-Goals

**Goals:**
- Provide a single, standalone Python 3 script `tools/package_firmware.py` that handles compilation, binary extraction, merging, and manifest generation.
- Ensure builds across different targets do not conflict or contaminate each other's build artifacts or configuration state.
- Output clean directory structures under `dist/<version>/<target>/` suitable for direct hosting and consumption by web flashers.
- Generate both split binaries and a unified `nesigner_merged.bin` at offset `0x0`.
- Generate `manifest.json` with target names, chip families, binary paths, flash offsets, and flash parameters.

**Non-Goals:**
- Direct automatic deployment or upload to remote web servers or Git repositories.
- Automatic modification of the `nesigner_website` web page source code (the web page consumes the output directory via configuration or copy).
- In-place modification of existing firmware source files in `main/` or `components/`.

## Decisions

### 1. Dedicated Python Packaging Script (`tools/package_firmware.py`)
- **Decision**: Implement a pure Python script utilizing standard library modules (`argparse`, `subprocess`, `json`, `shutil`, `pathlib`) and invoking `idf.py` and `esptool.py`.
- **Rationale**: Python is cross-platform, handles JSON manipulation natively, and is already part of the mandatory ESP-IDF virtual environment.
- **Alternatives Considered**: Shell scripts (`.sh`) were rejected due to poor Windows support and fragile JSON parsing dependencies (`jq`).

### 2. Isolated Build Directories (`build_<target>/`)
- **Decision**: Invoke `idf.py -B build_<target> set-target <target>` and `idf.py -B build_<target> build` for each target.
- **Rationale**: Running `set-target` inside the default `build/` directory invalidates CMake caches, triggers full recompilation, and risks stale config contamination. Separate directories allow reliable incremental builds when packaging repeatedly.
- **Alternatives Considered**: Cleaning `build/` between targets (`idf.py fullclean`) was rejected because it wastes considerable time re-compiling components common across builds.

### 3. Dynamic Flash Argument Extraction from `flasher_args.json`
- **Decision**: Parse `flasher_args.json` generated by ESP-IDF in each build directory to discover flash mode, flash frequency, flash size, and the exact offsets for `bootloader`, `partition-table`, and `app`.
- **Rationale**: Bootloader and partition offsets can vary across ESP32 chip architectures (e.g. 0x0 vs 0x1000). Dynamic extraction prevents firmware bricking caused by manual offset hardcoding.
- **Alternatives Considered**: Hardcoding table of offsets per chip was rejected due to fragility when partition tables or silicon revs change.

### 4. Merged Binary Generation via `esptool.py merge_bin`
- **Decision**: Run `esptool.py --chip <target> merge_bin -o nesigner_merged.bin --flash_mode <mode> --flash_size <size> --flash_freq <freq> <offset1> <bin1> ...` based on the parsed `flasher_args.json`.
- **Rationale**: Many Web Serial flashers (and offline tools) perform better flashing a single file at 0x0 rather than executing 3 separate erase/write cycles.
- **Alternatives Considered**: Only providing split binaries was rejected because web flashers experience higher failure rates with multi-part downloads and flashes.

### 5. Structured Manifest Format (`manifest.json`)
- **Decision**: Structure the manifest to include version, build timestamp, and an array of target descriptors with both split parts and merged binary references.
- **Rationale**: Provides complete flexibility for web flashers, whether they use `esptool-js` with individual files or `esp-web-tools` with merged images.

## Risks / Trade-offs

- **[Risk] Long build times when compiling all 7 targets sequentially** → Provide `--target` flag so developers can build only the target(s) they need during testing.
- **[Risk] Missing ESP-IDF environment when script is invoked** → Script checks for `IDF_PATH` and availability of `idf.py` at entry and halts with an actionable error message if unconfigured.
- **[Risk] ESP32-P4 or ESP32-C5 requiring preview target flags or specific IDF versions** → Script checks output and passes appropriate preview arguments if target registration requires it.
